# Changelog

All notable changes to this package are documented in this file.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the package uses [Semantic Versioning](https://semver.org/).

## [0.1.0] - Unreleased

### Added

- Package skeleton: manifest, assembly definitions, folder layout and documentation stubs.
- Smoke compute kernel and tests that prove assemblies compile, the shader is found and a dispatch works.
- CPU reference solver math layer (`McKrill.Avbd.Reference`): `Vec6`, `Mat6` with an LDL^T solver, and quaternion helpers (`AvbdQuat`), with Edit Mode tests.
- CPU reference solver (`ReferenceSolver`): a C# port of the upstream avbd-demo3d solver with boxes, contact manifolds (15-axis SAT, face clipping, edge contacts, feature-key warm start), ball-socket joints with optional angle lock and fracture, springs and IgnoreCollision. Includes the upstream demo scenes (`AvbdScenes`).
- Two primal-sweep orderings: `GaussSeidelMode.Sequential` (upstream's order) and `GaussSeidelMode.Colored` (greedy graph coloring, the order the GPU solver will run).
- Upstream-exact quaternion helpers (`AvbdQuat.Mul`, `Conjugate`, `Inverse`, `Rotate`, `Transform`, `DifferenceRaw`) and row/column-safe 3x3 helpers (`AvbdMat3`).
- Edit Mode tests: golden trajectories from the upstream C++ solver (`UpstreamParityTests`) and behavior, coloring, collision and fracture tests (`ReferenceSolverTests`).
- `THIRD_PARTY_NOTICES.md` with the upstream MIT attribution.
- Sample `Reference Solver Demo` (Package Manager > Samples): runs the CPU reference solver live with the upstream scenes, a sequential/colored toggle, graph-color tint, contact and joint overlays, and a drop-box button.
- Stage E of the GPU solver, for rigid boxes: per-body GPU arrays (`AvbdBodyBuffers`, 224 B per body), slot allocation with stale-handle detection, and an edit queue that merges spawn, remove and property edits into one command per slot. A compute kernel (`AvbdBodyEdits.compute`) clears the arrays and applies the commands. The HLSL and C# record definitions are checked against each other by a test.
- CPU oracle for stage E (`CpuBodyArrays`) and tests: layout, allocator, edit queue, and a GPU-versus-oracle comparison over random edit streams.
- Stage P of the GPU solver (predict): `AvbdSolverSettings`, `AvbdSolver` (`Step()` runs the stages that exist), the `AvbdPredict.compute` kernel, and the `CpuPredict` oracle. Tests check the oracle against the reference solver's predict phase and the kernel against the oracle.
- Stage V of the GPU solver (primal update): the `AvbdPrimal.compute` kernel solves each body's 6x6 system with an LDL^T factorization, one dispatch per graph color. Joints and springs are one 160 B `ConstraintRecord` (hard constraints are a flag, not an infinite stiffness); `AvbdConstraintBuffers` (`AddJoint`, `AddSpring`, `Rebuild`) owns them and builds the per-body lists on the CPU until stage G exists. `AvbdSolver.Step()` now also runs the primal sweeps.
- Stage D of the GPU solver (constraint variables): `AvbdDual.compute` with a `ConstraintInit` kernel (C0 at the start-of-step pose, warm start of multipliers and penalties) and a `Dual` kernel (multiplier and penalty update, fracture). `AvbdSolver.Step()` now runs predict, the warm start, and per iteration a primal sweep and the dual update.
- CPU oracle `CpuDual`, and `DualTests`: the oracles against the reference solver over a whole step, and the GPU solver against the oracles.
- Stage U of the GPU solver (velocity update): `AvbdVelocity.compute` derives each solved body's linear and angular velocity from its displacement over the step and snapshots the linear velocity for the next adaptive warm start. `AvbdSolver.Step()` now runs a whole step (edits, predict, warm start, iterations, velocity update). Oracles `CpuVelocity` and `CpuStep`; `VelocityTests` compares the oracle and the GPU solver with the reference solver over 60 steps on the rope and the spring scene, and checks a free fall against its closed form.
- `AvbdSolver` without constraint buffers now creates an empty set of its own, so free bodies get their primal solve; it is `IDisposable` and releases only what it created. The constraint lists are rebuilt when bodies are spawned, removed or change shape or kinematic state (`AvbdBodyBuffers.SolvedSetVersion`); before, a body spawned after the last `Rebuild()` was never solved.
- CPU oracles `CpuPrimal` and `CpuConstraintInit`, and tests: constraint layout, lists and coloring against the reference solver, the oracle against the reference solver after one colored iteration, and the kernel against the oracle.
- Design doc sections 3 and 5-10 (body arrays, capacity, slot allocation and edits, overflow policy, buffer owner, layout contract, tests).
- Stage C of the GPU solver (graph coloring): `AvbdColoring.compute` colors the solved bodies with Jones-Plassmann rounds and buckets them by color; `AvbdGraphColoring` runs it from `AvbdConstraintBuffers.Rebuild()`. The default `GraphColoringOrder.SlotOrder` gives exactly the reference solver's coloring; `GraphColoringOrder.Hashed` needs far fewer rounds on long chains. The graph color is stored in `Meta.state.x`. More than 64 colors throws. The CPU coloring in `ConstraintTopology` is now only the oracle (`CpuGraphColoring` adds the hashed order), and `GraphColoringTests` compares the GPU with it. Colors are recomputed on every rebuild; temporal coherence is not implemented.
- Sample `GPU Pyramid Demo`: a pyramid of 140 to 650 boxes (7 to 12 layers) on the GPU solver through the public API (`AvbdBodyBuffers`, `AvbdSolver.Step()`), a fly camera, left click to shoot a box in the direction the camera looks, and a panel for the shot's speed, size and mass, the solver iterations and the pyramid height. Includes the scene `PyramidShooter`. It contains no collision code and needs the contact stages inside `Step()`; until then the boxes fall through each other. It was written without access to a Unity editor and has not been run.
- Stage B of the GPU solver (broadphase): `AvbdBroadphase.compute` finds the pairs of overlapping bounding spheres with a hashed uniform grid (cell size from the largest radius, 27-cell search, atomic linked lists), tests solved bodies against the static ones by brute force, and skips pairs joined by a constraint that has not broken. The pair list (`PairRecord`, 16 B) has two bins, dynamic-dynamic and dynamic-static, with counted overflow. `AvbdSolver.EnableBroadphase` makes `Step()` run it; nothing consumes the pairs until the narrowphase exists. It applies the same candidate rule as the all-pairs narrowphase (joints and springs exclude a pair, even a fractured one; contacts do not), but the narrowphase does not read the pair list yet. `CpuBroadphase` is the oracle and `BroadphaseTests` compares it with the reference solver's pair loop, the GPU with it, and checks that every pair with contacts is a broadphase pair. Pair order is unspecified; static colliders are in the pair list (a deviation from the scope paragraph of the design doc, documented in the stage B section); `IgnoreCollision` is not represented.
- Sample *JSON Mesh Import Demo*, based on the GPU Fracture Wall Demo: instead of a wall it spawns the objects of every voxel file (the JSON of `Tools/Voxelize/voxelize_stl.py`) in a `Resources/JsonMeshImportDemo` folder, one each in the order of the file names, 5 m apart along x. Every voxel is a box body and every joint of the file is a ball-socket joint with a rigid angle lock that fractures like the wall's. There is no list in the code: adding a `.json` file to the folder adds an object. The sample ships a sphere, a torus and a cube (made from a hollow mesh) there. `Reset` reads the folder again, and a file that cannot be read is reported and skipped. Shots, explosions and plastic joints work as in the wall demo; the volley and the wall settings do not apply, and the voxel mass replaces the block density. Includes the scene `JsonMeshImport`. Written without a Unity editor: not compiled, not run.

### Notes

- The stage B code and tests were written without access to a Unity editor or a GPU and have not been run.
- The stage U code and tests were written without access to a Unity editor or a GPU and have not been run. The speed limit listed for stage U in the design doc is not implemented (upstream has none).
- The stage E code and tests were written without access to a Unity editor or a GPU and have not been run. Growth of the buffers beyond their initial capacity is not implemented yet; `Spawn` returns an invalid handle when the buffers are full.
- Gravity is a vector (`AvbdSolverParams.gravity`), default `(0, 0, -10)` to match upstream's z-up demo scenes; use `(0, -10, 0)` for Unity's y-up.
- `AvbdQuat.Difference` flips the sign when `w < 0`; upstream does not. The solver uses upstream's `DifferenceRaw` unless `AvbdSolverParams.canonicalizeQuatDifference` is set.
- The reference solver compiles and its Edit Mode tests pass in Unity 6.6. The Reference Solver Demo sample has not been run in a Unity editor yet.
- Contacts without a broadphase (stage N): box-box contacts from testing every pair of bodies, like the reference solver, up to 512 bodies (`new AvbdConstraintBuffers(bodies, capacity, null, contactBodies)`). `AvbdNarrowphase.compute` runs one thread per pair (15-axis SAT, face clipping, feature-key warm start); the primal kernel stamps contact rows and a `DualContact` kernel updates multipliers and penalties. Contacts are `ConstraintRecord`s of kind `Contact` in a dense per-pair region (8 per pair); the lists are rebuilt on the CPU from a pair-count readback each step until stage G exists, and stage C colors the graph with the contacts in it. Pairs joined by a joint or spring do not collide; ignore-collision pairs are not supported.
- Stage N reads the broadphase's pair list (rework): manifolds live in a pool of slots (`new AvbdConstraintBuffers(bodies, capacity, null, contactCapacity)`; this argument was `contactBodies`) instead of a slot per pair of body slots, so the cost no longer grows with the square of the bodies and the 512-body limit (`MaxContactBodies`) is gone. Pairs of the broadphase take a free slot when their boxes collide and give it back when they stop; a hash table rebuilt every step maps a pair to its slot, so warm starts find the previous contacts. The narrowphase runs as four kernels (`NpClearTable`, `NpRetire`, `NpAllocate`, `Narrowphase`), the broadphase runs automatically with contacts, and the lists are still built on the CPU after a readback (stage G). `AvbdConstraintBuffers.ReadContacts()` reports the pool. The CPU oracle keeps the dense all-pairs semantics and the GPU is compared with it. Limits: a fixed number of slots (a new pair with no free slot gets no contacts until one frees), and the pool's `Overflow` count.
- CPU oracle `CpuContacts` (and a contact branch in `CpuPrimal`, `CpuStep`) and `ContactTests`: topology, manifolds against the reference solver, ground and stack trajectories, GPU narrow phase against the oracle, GPU steps against the reference solver, recycled slots.
- `Tools/HlslParity`: builds the contact HLSL as C++ and compares it with upstream's unmodified solver (narrow phase and contact math), bit-identical on about 800 000 cases.
- `AvbdQuaternion.hlsl` split out of `AvbdMath.hlsl`.
- With contacts, a fractured joint is dropped from the constraint lists and the coloring one step after it broke, so the pair stops being excluded from collisions at the reference solver's timing (`AvbdConstraintBuffers.BrokenCount`). The joints' broken flags are read back each step, only if some joint can fracture.
- Sample *GPU Fracture Wall Demo*: a running-bond wall of 225 to 396 blocks (15 x 15 by default) with an immobile bottom row, held together by fracturing joints, shot from the camera like the pyramid demo, with a panel for the wall's size, density, joint stiffness and fracture threshold. A *Walls* slider (1 to 10, default 1) spawns several walls one behind the other, 4 m apart.
- Stage G of the GPU solver (constraint lists on the GPU): `AvbdLists.compute` counts the constraints of each solved body, scans the counts into offsets, fills the lists and sorts each one into the CPU oracle's order (contacts by pair and k, then joints and springs newest first). `Rebuild()` and `RefreshContactTopology()` no longer read the manifold pool, the joint flags or the body flags back, and no longer build the lists on the CPU; `ConstraintTopology` stays as the oracle. A fractured joint is left out by reading its `Broken` flag on the GPU, with the same timing as before. `AvbdConstraintBuffers.BrokenCount` now reads a GPU counter (once per list build) instead of a per-step readback. The graph coloring still reads the color counts back. `ConstraintListTests` compare the GPU lists with the oracle entry by entry.
- The broadphase no longer walks the contact entries of a body's constraint list when it tests whether a joint or spring joins a candidate pair. Stage G writes the number of contact entries (the first ones of the list) into `Range.z`, and `Constrained()` starts after them. The cost of that test was proportional to the contacts of the body and was paid for every overlapping candidate pair (and for every body against every static body), so it grew with how much a pile touches. `ConstraintTopology` fills `Range.z` too, and `ConstraintListTests` compare it.
- Broadphase: dynamic-static pairs no longer test every solved body against every static body (`BpPairsStatic` was the longest kernel with 20000+ bodies and many static bodies). Static and kinematic bodies whose bounding sphere is no larger than the largest solved body's now share the grid with the solved bodies (flag `AVBD_BP_STATIC_FLAG` in `_BodyCell.w`, `AvbdBroadphase.StaticCellFlag`) and are found by the same 27-cell walk, so the cost of a solved body depends on the static bodies near it, not on their total number; the grid is rebuilt every run, so moving kinematic bodies need nothing special. Static bodies larger than every solved body (a ground slab) stay in a list that every solved body is tested against (`BpPairsStatic`, `AVBD_BP_STATIC_COUNT` now counts those). The set of pairs is unchanged (`BroadphaseTests`, new test `Gpu_MatchesTheOracle_WithManyStaticBodiesOfDifferentSizes`). Written without a Unity editor or a GPU and not run.
- Broadphase: replaced by a reimplementation of three-avbd's grid. A counting-sort (CSR) grid (count per hashed cell, block scan, scatter) with the cell of each body stored beside the list, a fine and a coarse level when the moving bodies are much smaller than the static pieces, and a list of at most 64 large bodies (ground slabs) tested against everybody. Which bodies are large and how big the cells are is decided on the GPU from log histograms of the radii (`BpHistogram`, `BpClassify`; 16 bins per octave), so no readback is needed. Kernels `BpInsert`, `BpBounds`, `BpPairsDynamic` and `BpPairsStatic` are replaced by `BpHistogram`, `BpClassify`, `BpCount`, `BpScanBlock`, `BpScanTop`, `BpScanApply`, `BpScatter`, `BpPairs` and `BpPairsFixed`; `AVBD_BP_STATIC_COUNT` is now `AVBD_BP_LARGE_COUNT` and the control buffer has 1296 words. The set of pairs is unchanged (`BroadphaseTests` against the brute-force oracle; new tests for two levels, many large bodies, classification following `SetShape`, and a table larger than one scan block). `AvbdBroadphase.ReadMaxRadius()` now returns the upper edge of the radius bin (at most 4.4% above the radius); `ReadClassification()` is new. Written without a Unity editor or a GPU: not compiled, not run, not measured.
- `AvbdBodyBuffers.SpawnBatch` and `SpatialOrder`: a scene's bodies can be spawned in one call and are placed in Z-curve (Morton) order of their positions, so that bodies that touch each other are near each other in the GPU arrays (the solver reads partner poses by slot; three-avbd's `spatialSort`, comparison doc section 7). The handles come back in the order of the descriptors. The brick ring and fracture wall performance scenes use it; `Scenario5_BrickRing110k_BuilderOrder` and `Scenario1_Shots2m_PlasticYieldOff_BuilderOrder` keep the old order as a baseline. Editor tests: `SpatialOrderTests`. Written without a Unity editor or a GPU: not compiled, not run, not measured.
- Sample *GPU Brick Ring Demo*: the 110 440-brick ring of the performance test `Scenario5_BrickRing110k`, with the ball, shots, size settings and a switch between builder order and Z-curve order of the bodies. The *GPU Fracture Wall Demo* got a **Fire volley** button (key `V`), which fires the 15-shot volley of the performance tests `Scenario1` to `Scenario4`, and the same body-order switch. Written without a Unity editor: not compiled, not run.
- `Shaders/Rendering/AvbdInstancedBoxes.shader` (referenced by `AvbdShaderSet.InstancedBoxes`): draws boxes straight from the solver's body state buffer, one instance per box, for the built-in pipeline and URP (no shadows). The *GPU Fracture Wall Demo* uses it, so the demo no longer reads the poses back every frame or keeps a GameObject per body; the cost of drawing no longer grows with the body count that way. The pyramid demo is unchanged. Written without a Unity editor and not run.
- Compact contacts (point 4 of `Docs/design/three-avbd-comparison.md`, section 3): the manifold pool stores a contact as a 64 B point (`ContactPointRecord`) and each manifold as a 32 B pair record (`ContactPairRecord`: bodies, number of points, stick bits, normal, friction) instead of eight generic 160 B `ConstraintRecord`s, so a slot takes 544 B instead of 1.3 kB and `MaxContactManifolds` is 272 MB. The lists have one entry per manifold (`AVBD_LIST_CONTACT_FLAG | slot`) instead of one per contact point, the primal sweep loads the two bodies and makes the contact basis once per pair (`AvbdEvaluateContactInBasis`), and the contact dual update is one thread per manifold (`PoolArgsDual` is the high-water mark, not eight times it). `_PairCounts`, `_SlotBodies` and `_ContactBase` are gone (`_ContactPairs` and `_ContactPoints` replace them), the stick bit moved from the record flags to the pair record, and `AVBD_CONSTRAINT_KIND_CONTACT` and `AVBD_CONSTRAINT_FLAG_STICK` are no longer in HLSL. Joints and springs, the CPU oracles and the HLSL parity tool are unchanged; the tests read contacts through `AvbdConstraintBuffers.ReadContactRecords`, `ReadContactRecord` and `WriteContactRecord`, which convert to the oracle's per-contact records. Written without a Unity editor or a GPU and not run or measured.
- Indirect dispatch of the primal sweep: stage C's new `ColorPlan` kernel leaves the start and the size of every color and the arguments of one indirect dispatch per color on the GPU, and `AvbdSolver` calls `DispatchIndirect` for each color. The second coloring readback (the per-color counts) and the upload of the bucket cursors are gone; the number of colors now comes in the words of the first readback (`ColorRound` keeps an atomic max), so the coloring is down to one readback (are bodies still waiting) and the host only knows how many colors there are. The primal kernel reads `_Color` and `_ColorWork` instead of `_Base` and `_Count`. Colors bigger than 4.19 million bodies are laid out in rows of 65,535 groups. `AvbdConstraintBuffers.ColorOffset` and `ColorSize` now read the GPU on demand (for tests and tools). `AvbdGraphColoring.Run` no longer returns offsets. Tests: `IndirectSweepTests`.
- The indirect arguments buffer is created as `GraphicsBuffer.Target.IndirectArguments | Raw` and written from a `RWByteAddressBuffer`. This was written without a Unity editor or a GPU and has not been run; if a platform rejects that combination, it fails when the first `AvbdConstraintBuffers` is created.
- Performance, from a GPU profile of a few thousand interacting bodies. Stage G keeps a sort key and the neighbor body of every list entry next to the list: the sort compares contiguous keys instead of reading a constraint record per comparison, and the coloring rounds read the neighbor array (skipping the repeated neighbors of a pair's contacts) instead of dereferencing a record per entry. `AvbdConstraintLists` now takes the list capacity; `AvbdGraphColoring.Run` takes the neighbor buffer. `DualContact` (one thread per contact record, indirect since the merge of the indirect narrow phase) writes back only the three words that change, not the whole 144-byte record. `ConstraintListTests` also compare the neighbor array with the oracle.
- Cooperative primal sweep, from the same GPU profile (the sweep was the biggest item, 15 ms at about 6500 bodies, and bound by the serial walk of each body's constraint list, not by the number of bodies): `AvbdPrimal.compute` now gives a body `AVBD_PRIMAL_LANES` (8) threads that stamp its constraints in parallel, add the partial 6x6 systems in groupshared memory and solve once. `ColorPlan` sizes the indirect dispatch as 8 threads per body (`AvbdGraphColoring.PrimalLanes`, `GroupsFor` and the tests follow). The sum of the lanes is in another order than the oracle's, so results agree to rounding. Written without a Unity editor or a GPU and not run; the gain has to be measured by profiling again.
- Performance of stage G (`BuildLists`, which grows with the number of bodies) and stage C (`Recolor`), without changing the lists or the colors. Stage G: the prefix scan is three kernels (block scan, scan of the block sums, apply) instead of one group of 1024 threads with strided reads (up to 1024 x 1024 bodies); the contact kernels are dispatched indirectly over the manifold slots below the pool's high-water mark (the narrow phase's retire arguments) and not over every slot; the sort is a rank sort with 8 threads per body that reads unsorted key and item arrays and writes the sorted list and the other-body array out of place (no insertion sort in global memory, no constraint record read per entry); the contact count of a body is counted with the counts; `ListBegin` is gone. Stage C: a round uses 8 threads per body that read each neighbor's color once and or their reports in groupshared memory (the wait check and the used colors in one pass, instead of two serial walks), and the first batch of rounds is 16, so a usual graph needs one readback, not two or three. The lists and colors are the same as before. Written without a Unity editor or a GPU and not run; the gain has to be measured by profiling again.
- Indirect dispatch of the narrow phase and of the dual update of the contacts: the manifold pool keeps a high-water mark (`_NpControl[AVBD_NP_HIGH_WATER]`, the highest slot ever taken + 1, raised by `NpAllocate`), and a new one-thread kernel `NpPlan` turns it and the broadphase's pair counters into indirect dispatch arguments (`ContactLayout.PoolArgs*`, `AvbdConstraintBuffers.NpArgsBuffer`). `NpRetire`, `NpAllocate` (once per bin, `_Bin`), `Narrowphase` and `DualContact` are dispatched with `DispatchIndirect` over the slots that have been in use and the pairs that were found, not over the capacity of the pool and of the bins; the host reads no count. `DualContact` reads `_NpControl` and `_SlotCapacity` instead of `_Base` and `_Count`. The row layout of a big dispatch moved to `AvbdIndirect.hlsl` / `AvbdIndirect.cs`, which the coloring's mirror now uses too. `ContactLayout.PoolControlWords` is 3. `ContactSnapshot` has `HighWater` and `AvbdConstraintBuffers.ReadNpArgs()` reads the planned arguments. Tests: `ManifoldPoolTests`, `BodyLayoutTests`. Written without a Unity editor or a GPU, not run.
- Click mode *Throw* in the samples *GPU Fracture Wall Demo* and *JSON Mesh Import Demo*: the first left click casts a ray on the GPU and selects the box it hits and every box joined to it by joints that have not fractured (drawn in green); the next click throws the selection from the middle of the screen, the way a shot is fired, at the speed of a slider (5 to 200 m/s). A group that is still joined to an immobile block (the wall's bottom row) is selected but cannot be thrown until those joints break. The JSON demo's click mode is now a row of buttons (Shot, Explosion, Throw). New `AvbdConstraintBuffers.ReadIntactJointLinks`: the body slots of the joints that have not fractured, read back from the GPU for a click (not for every frame).
- Linear fracture and plasticity of joints (`Docs/design/gpu-data-layout.md`, section 12): `AddJoint(..., fracture, yield, bendLimit, fractureLinear, yieldLinear, stretchLimit)`. The linear row of a joint can break when its multiplier is above `fractureLinear`, yield when it is above `yieldLinear` (the multiplier is held at the yield value and the anchor on body A moves to where the anchor on B is, so the joint keeps the stretch instead of pulling back), and break once the anchor has moved more than `stretchLimit` meters. The state is the anchor in the constraint record the primal stage already reads, so only the dual kernel changed, with no new kernel variant and no extra cost for joints without the flags. **Hard linear rows only:** a soft (finite stiffness) row has no multiplier to test, so `AddJoint` throws for a finite `fractureLinear` or `yieldLinear` with a finite linear stiffness (as for the angular row). New flags `FracturableLinear`, `PlasticLinear`, `StretchBreak`; the linear fracture value is in word 9 of the `ConstraintRecord`, and `PlasticRecord.limits` holds the linear yield and the stretch limit. The reference solver, the CPU oracle and the tests follow. Not compiled or run in Unity.
- Samples *GPU Fracture Wall Demo* and *JSON Mesh Import Demo*: controls for linear fracture, linear yield and the stretch limit (they need rigid joints; off by default, applied on Reset).
- Dual kernel traffic: the dual update stores only the words of a joint record that it can have changed (the penalties and multipliers every call; the flags, the anchor on A and C0 only when a joint breaks or yields) instead of the whole 160 B record, reads only the limits and the rest rotation of a plastic joint (the other two words of its plastic record only when it breaks or yields), and compares squared norms for yield and fracture (a square root only when a row yields). Same results; less memory traffic for every joint in every iteration, which should offset the cost that the linear fracture and plasticity code added to scenes with plastic joints. Not compiled or measured (no Unity or GPU here).
- Primal kernel (from a GPU trace): the LDL^T solve of lane 0 runs in groupshared memory (`gsSums`, in place) instead of on a local array of 42 floats, so those registers are free; the 6x6 sums are written straight to it, without the copy; the pose is written as its two words (position, rotation) instead of the whole 64 B record, with no read back of the record; every read a body needs (flags, mass, pose, list range, inertial target) is requested together instead of one after another; and a lane takes the entries of its share in batches (`AVBD_PRIMAL_BATCH`, 2): the entries and the joint and spring records of a batch are requested before the first stamp, so the dependent loads of several stamps overlap. `AvbdSolveLdlt6` left `AvbdMath.hlsl` (the primal kernel was its only user). Same results, to rounding. A batch of 2 holds two 160 B records in registers: if the trace shows that occupancy dropped, set `AVBD_PRIMAL_BATCH` to 1. Not compiled or measured (no Unity or GPU here); the term mapping and the factorization were checked on the CPU against a float64 solve.
- Primal kernel, shared memory: the lanes of a body now pack their system into 27 terms (the solver only reads the lower triangle of the linear and angular blocks) and add the partial systems in two steps (the upper half of the lanes writes, the lower half adds and writes the result), so a 64-thread group uses 4.3 KB of groupshared memory instead of 9.5 KB, which can raise the number of resident groups per SM. The solve reads the same numbers as before; only the order of the additions of the lanes changed (to rounding). One barrier more per dispatch. Not compiled or measured (no Unity or GPU here); the term mapping, the reduction and the solve were checked on the CPU against a float64 solve.
- Primal kernel, joint stamp: `StampJoint` writes the Jacobian products out (the linear Jacobian is sgn * I, the angular one a skew matrix, the penalty matrices are diagonal) instead of building 3x3 matrices, transposes and products, and takes the column lengths of the geometric-stiffness term from its three column vectors. Fewer temporaries, so fewer registers in the register-bound primal kernel. Same numbers to rounding (the entries were compared with the matrix form on the CPU, relative difference 6e-16). Not compiled or measured (no Unity or GPU here).
- Plastic joints (joint plastic yield and bend-break, after three-avbd; `Docs/design/gpu-data-layout.md`, section 12): `AddJoint(..., fracture, yield, bendLimit)`. A joint with a hard angle lock and a finite `yield` gives way when its angular multiplier is above it: the multiplier is held at `yield` and the rest rotation of the joint moves to the current relative rotation, so the joint keeps the bend instead of springing back (the yielding row does not ramp its penalty). A finite `bendLimit` (radians, up to pi) breaks a joint that has bent further than that from its original rest rotation. A multiplier above the fracture threshold still breaks the joint instead of yielding. The angular row now holds `rotB = rotA * rest` (`AvbdJointAngularError`); `rest` is the identity for a joint that never yields, which computes what it did before. The state is a 64 B `PlasticRecord` in a separate array (`ConstraintRecord.ident.w` is its slot; new flags `Plastic` and `BendBreak`), so the 160 B constraint record and the memory traffic of joints that are not plastic are unchanged. It exists only if the buffers are made with `new AvbdConstraintBuffers(bodies, capacity, shaderSet, contactCapacity, plasticCapacity)` (default 0): then `AvbdSolver` runs the joint kernels without any plastic code (`AVBD_PLASTIC_JOINTS`, a `multi_compile_local` keyword the solver sets before each dispatch). `AddJoint` throws for a plastic joint without a plastic capacity, without a hard angle lock, or with invalid values, warns once if the fracture threshold is not above the yield value, and returns -1 (counting an overflow) when the plastic slots are used up. Oracles: `CpuConstraintInit`, `CpuDual`, `CpuPrimal`, `CpuStep` take the plastic array (`CpuPlastic`), and the reference solver's `AvbdJoint` has `yield`, `breakBend`, `rest`. Tests: layout, oracle against the reference solver and by hand, and the GPU kernels against the oracle. Not run: written without a Unity editor or a GPU.
- Sample *GPU Fracture Wall Demo*: the panel has plastic yield controls (a toggle, the yield threshold on a log scale, and a bend break toggle with a limit in degrees; off by default, applied on Reset). The wall defaults to 75 columns, 75 rows and 10 walls (56 250 blocks), the title line is gone, and the columns, rows and walls sliders (labelled C, R and W) share one row above the total block count.
- Broadphase: a candidate pair whose bounding spheres overlap is now dropped when its boxes are visibly apart: the world bounding boxes do not overlap, or a face axis of either box separates them by more than 1 mm (`BoxesSeparated`, `AVBD_BP_SEPARATION_PAD`). The narrow phase finds no contact for such a pair, so no manifold changes, but `NpAllocate` no longer repeats a full collision test for it every step. The CPU oracle has the same test; the tests check that it never drops a pair with contacts, and the broadphase tests now accept the reference solver's pairs minus pairs without contacts. The idea is from three-avbd's broadphase (their measurement: -15% on a brick ring). Written without a Unity editor or a GPU: not compiled, not run, not measured.
- Persistent graph coloring with asynchronous tuning (point 2 of `Docs/design/three-avbd-comparison.md`): with contacts, the coloring keeps the colors of the step before and recolors only the bodies that have the color of a neighbor that colors before them (`ColorKeep`, `ColorMark`, `ColorRelease`), by a fixed number of Jones-Plassmann rounds, then up to 8 more that are dispatched indirectly and run only while bodies wait, and a last kernel (`ColorForce`) for the rare body that is still without a color, so the result does not depend on the number of rounds. The host no longer waits for the GPU: the sweep dispatches a cap on the number of colors, and `ColoringTuner` raises the rounds and the cap at once and lowers them slowly from statistics read back with `AsyncGPUReadback`. A body without a free color below the cap shares the last one for a few steps. - Explosions: `AvbdSolver.Explode(center, radius, impulse)` queues a radial impulse that stage P applies in the next step (`PredictExplosions` kernel variant, so steps without explosions run the old code; at most 16 per step). The velocity change is `impulse (1 - r/R)^2 / mass` along the line from the center, with a small hashed off-center angular kick, no upward bias and no shock shell. - Sample *GPU Fracture Wall Demo*: a button switches the left click between shooting boxes and explosions. In explosion mode the panel shows Radius, Force and Depth instead of the shot's speed, size and mass. The ray is cast on the GPU with `AvbdRaycaster` (new: `AvbdRaycast.compute`, `AvbdShaderSet.Raycast`; `Cast` tests every live body's box and returns the nearest hit distance through an asynchronous readback of four bytes), so the poses are not read by the CPU. No visual or audio effect.
- Force fields: `AvbdSolver.AddForceField`, `UpdateForceField` and `RemoveForceField` add a force that acts on a group of bodies in every step (at most 16). The group is the bodies whose group mask shares a bit with the mask of the field, so the label is the group mask that every body already has and no per-body data is added. Kinds: `Constant` (a force in N, world or body frame), `GravityScale` (a body that falls as if gravity were scale times as strong), `Drag` (linear and quadratic, with a wind) and `Wing` (lift and drag on a flat plate: an airplane gets lift only from the blocks of its wings). Applied by the new `PredictForces` and `PredictForcesExplosions` kernel variants, which add the acceleration to the inertial target; steps without fields run the plain kernel. Oracle `CpuForceFieldMath` and `ForceFieldTests` (`Docs/design/gpu-data-layout.md`, stage P).
- Spring force fields (`ForceFieldDescriptor.Spring`): a damped spring that pulls the centroid of a group toward a target, so every body of the group gets the same force and the group keeps its shape. The centroid is summed on the GPU in fixed point (`ForceFieldClear` and `ForceFieldAccumulate` kernels, 256 B); it is added to the force field table of the predict stage only when a spring exists.
- `AvbdGroupLabeler`: changes the group mask of the bodies within a radius of a point on the GPU (`AvbdGroupLabel.compute`), to pick a group of bodies for a force field from a ray hit. `AvbdShaderSet` has a new `GroupLabel` entry.

### Changed

- `AvbdGroupMover` (`AvbdGroupMove.compute`, `AvbdShaderSet.GroupMove`): moves every body of a group directly on the GPU, by a translation of the position and/or by setting the linear and angular velocity, without touching mass, inertia or anything else (not a force, not a kinematic body). `BeginHold`/`Hold` (kernels `HoldCapture`, `HoldApply`) place every body of a group on its own relative to a moving point: `BeginHold` stores, on the GPU, the offset of each body from the point (one float4 per body slot), and `Hold` puts each body at the point plus its own offset and gives it the velocity of the point. The positions are absolute, so what a step did to the bodies (gravity, contacts) is undone at the next call and the group does not sink (adding a distance cannot do that), while the group keeps its arrangement. Angular velocity and rotation are not changed. The GPU Fracture Wall Demo's Grab has a *Direct* toggle that uses it instead of the spring force: once a frame, before the steps, each grabbed block is placed at the point at the center of the screen plus its own offset with the velocity of that point, so the blocks follow the camera exactly whatever the number of steps in a frame, and they can be thrown.
- The demos (GPU Brick Ring, GPU Fracture Wall, GPU Pyramid, Reference Solver) always run 2 solver steps per frame, with the fixed time step, instead of fitting the steps to the frame time (no accumulator, no `maxStepsPerFrame`, no "running slower than real time" label). The simulation advances 2 steps per frame, so its speed follows the frame rate.
- JSON Mesh Import Demo: every AVBD solver setting (time step, iterations, gravity, alpha, beta linear and angular, gamma, lowest and highest penalty) has a control in the panel at the right of the screen, below the objects; they apply at the next step without a Reset. Fixed a missing semicolon after `settings.penaltyMin = 2000f` (a compile error). Not compiled, not run.
